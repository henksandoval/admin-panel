# Test Cases: ErrorInterceptor

| ID del Test | Tipo | Escenario / Propósito | Precondiciones | Pasos clave | Resultado Esperado | Justificación de Valor |
|---|---|---|---|---|---|---|
| TC-ServerSideError-Notification | Integración | Errores de servidor (4xx/5xx) muestran una notificación con el código de estado | Servidor responde con `HttpErrorResponse` (ej. status 500) | 1. Realizar petición HTTP. 2. Servidor responde con error 500. | `NotificationService.error()` es llamado con un mensaje que incluye el código de estado. El error es relanzado. | Garantiza visibilidad inmediata de errores de backend al usuario; sin esto, los fallos de API pasan desapercibidos. |
| TC-ClientSideError-Notification | Integración | Errores del lado del cliente (red caída, timeout) muestran una notificación apropiada | La petición falla con un `ErrorEvent` (ej. error de red) | 1. Realizar petición HTTP. 2. La petición falla con `ErrorEvent`. | `NotificationService.error()` es llamado con el mensaje del `ErrorEvent`. El error es relanzado. | Diferencia entre errores de red y de servidor; crítico para que el usuario sepa si el problema es de conectividad o del backend. |
| TC-ErrorPropagation | Integración | El error HTTP siempre se propaga al componente tras mostrar la notificación | Cualquier error HTTP | 1. Suscribirse al observable de la petición. 2. Servidor responde con error. | El subscriber del observable recibe el error; el interceptor no lo absorbe silenciosamente. | Previene que los componentes pierdan la capacidad de manejar errores específicos (ej. redirigir en 404, reintentar en 503). |
