# Test Cases: AuthService

| ID del Test                      | Tipo        | Escenario / Propósito                                                      | Precondiciones                                                          | Pasos clave                                                                                                                               | Resultado Esperado                                                                                                                        | Justificación de Valor                                                                                                          |
|----------------------------------|-------------|----------------------------------------------------------------------------|-------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------|
| TC-CheckSession-Success          | Integración | Sesión restaurada correctamente al inicio de la aplicación                 | Provider retorna un TokenResponse válido al llamar `refreshAccessToken` | 1. Llamar `checkSession()`. 2. Provider emite TokenResponse. 3. Provider retorna AuthUser al llamar `getUser`.                            | `status` = `'authenticated'`, `currentUser` tiene datos del usuario, `accessToken` tiene el token.                                        | Valida el flujo crítico de recuperación de sesión en cold start; si falla, ningún usuario autenticado podrá recargar la página. |
| TC-CheckSession-NoToken          | Integración | Sin sesión previa, el estado queda `unauthenticated` sin redirigir         | Provider lanza un error en `refreshAccessToken`                         | 1. Llamar `checkSession()`. 2. Provider lanza error.                                                                                      | `status` = `'unauthenticated'`, sin redirección al login.                                                                                 | Garantiza que la ausencia de sesión no bloquea la app ni muestra un error al usuario; el flujo de inicio debe ser silencioso.   |
| TC-Login-Success                 | Integración | Login exitoso establece estado y redirige                                  | Provider responde con TokenResponse y AuthUser válidos                  | 1. Llamar `login({email, password})`. 2. Provider emite TokenResponse. 3. Provider emite AuthUser. 4. `router.navigateByUrl` es invocado. | `status` = `'authenticated'`, `currentUser` con datos del usuario, router navega a `redirectAfterLogin`.                                  | Cubre el happy path del login; es el flujo de negocio más crítico de toda la aplicación.                                        |
| TC-Login-WithReturnUrl           | Integración | Login exitoso redirige a la URL de retorno en vez de la ruta por defecto   | El usuario accedió a una ruta protegida antes de autenticarse           | 1. Llamar `login(credentials, '/dashboard/reports')`. 2. Login exitoso.                                                                   | Router navega a `/dashboard/reports` en vez de `AUTH_DEFAULTS.redirectAfterLogin`.                                                        | Evita la pérdida de contexto del usuario; es un caso crítico de UX para rutas protegidas.                                       |
| TC-Login-InvalidCredentials      | Integración | Credenciales inválidas propagan el error sin modificar el estado           | Provider lanza un error al llamar `login`                               | 1. Llamar `login({email, password})`. 2. Provider lanza un error.                                                                         | Error propagado al subscriber. `status` permanece sin cambios. `currentUser` sigue siendo `null`.                                         | Previene que una respuesta de error deje el estado de autenticación en un valor corrupto.                                       |
| TC-Logout-Success                | Integración | Logout limpia la sesión y redirige al login                                | Usuario autenticado con sesión activa                                   | 1. Llamar `logout()`. 2. Provider completa `logout()`.                                                                                    | `status` = `'unauthenticated'`, `currentUser` = `null`, `accessToken` = `null`, router navega a `loginRoute`.                             | Verifica que los artefactos de sesión se limpian correctamente para evitar accesos no autorizados post-logout.                  |
| TC-Logout-ProviderFailure        | Integración | Fallo en la API de logout igual limpia la sesión local                     | Provider lanza error en `logout()`                                      | 1. Llamar `logout()`. 2. Provider lanza error.                                                                                            | `status` = `'unauthenticated'`, `currentUser` = `null`, router navega al login. El observable completa sin error para el subscriber.      | Garantiza que un fallo de red no deje al usuario "atrapado" en un estado autenticado sin poder salir.                           |
| TC-TokenRefresh-TimerScheduled   | Integración | El refresh automático de token se programa correctamente tras autenticarse | Login exitoso con token que expira en más de 60 segundos                | 1. Login exitoso con `expiresInSeconds = 900`. 2. Avanzar el timer virtual.                                                               | `refreshAccessToken` del provider es llamado antes del vencimiento del token (en `expiresInSeconds * 1000 - tokenRefreshThresholdMs` ms). | Previene que la sesión expire de forma silenciosa durante el uso activo de la aplicación.                                       |
| TC-TokenRefresh-AlreadyExpired   | Componente  | No se programa un timer si el token ya está en el umbral de expiración     | `expiresInSeconds` resulta en un delay ≤ 0                              | 1. Login exitoso con `expiresInSeconds = 30` (menor al umbral de 60s).                                                                    | No se crea un `setTimeout`. El usuario es redirigido al login al próximo intento de acción protegida.                                     | Evita timers con delay negativo o cero que ejecutarían el refresh de forma inmediata e inesperada.                              |
| TC-HasRole-CheckRole             | Componente  | `hasRole` retorna signal correcta según los roles del usuario              | Usuario autenticado con roles `['admin', 'editor']`                     | 1. Llamar `hasRole('admin')`. 2. Llamar `hasRole('viewer')`.                                                                              | `hasRole('admin')` retorna `true`; `hasRole('viewer')` retorna `false`.                                                                   | Valida la lógica de autorización basada en roles que protege secciones de la UI y rutas.                                        |
| TC-HasPermission-CheckPermission | Componente  | `hasPermission` retorna signal correcta según los permisos del usuario     | Usuario autenticado con permissions `['read', 'write']`                 | 1. Llamar `hasPermission('write')`. 2. Llamar `hasPermission('delete')`.                                                                  | `hasPermission('write')` retorna `true`; `hasPermission('delete')` retorna `false`.                                                       | Valida el sistema de autorización granular a nivel de permisos, esencial para controlar acciones específicas.                   |
