## Critical Circuits

Eight circuits. One or two scenarios each. Every test is a contract: if it fails, the feature is broken for the user.

---

### Circuit 1 — Login Success

| | |
|---|---|
| **Origin** | spec CA-04: "Dado credenciales válidas → redirigido al panel" |
| **File** | `auth.service.spec.ts` |
| **State** | ✅ GREEN (existing) |

**GIVEN** a user submits valid credentials  
**WHEN** `AuthService.login()` completes  
**THEN** `status` becomes `'authenticated'`, `currentUser` is populated, and the router navigates to `redirectAfterLogin`

---

### Circuit 2 — Login Failure

| | |
|---|---|
| **Origin** | spec CA-21: "Correo o contraseña inválidos" + non-functional "no revelar si el usuario existe" |
| **File** | `auth.service.spec.ts` |
| **State** | 🔴 RED — fails until `AuthService.login()` normalises HTTP 401 (GAP-4) |

**GIVEN** a user submits invalid credentials  
**WHEN** the provider returns HTTP 401  
**THEN** the rejected error carries the message `'Correo o contraseña inválidos'` and session status remains unchanged — the message does not reveal whether the account exists

---

### Circuit 3 — Protected Route (No Auth)

| | |
|---|---|
| **Origin** | spec CA-01: "usuario NO autenticado → redirigido al login" |
| **File** | `auth.guard.spec.ts` |
| **State** | ✅ GREEN (existing) |

**GIVEN** an unauthenticated user  
**WHEN** they navigate to `/dashboard`  
**THEN** `authGuard` redirects to `/auth/login?returnUrl=%2Fdashboard` without processing the protected URL

---

### Circuit 4 — Logout

| | |
|---|---|
| **Origin** | spec CA-11 + CA-12: "sesión destruida, URL protegida redirige al login" |
| **File** | `auth.service.spec.ts` |
| **State** | ✅ GREEN (existing) |

**GIVEN** an authenticated user calls `logout()`  
**WHEN** the operation completes  
**THEN** `status` becomes `'unauthenticated'`, `currentUser` and `accessToken` are null, and the router navigates to the login route

### Circuit 7 — Idle Auto-Logout

| | |
|---|---|
| **Origin** | spec CA-08: "no actuar en 2 min → sesión se cierra automáticamente" (GAP-2 criticality: HIGH) |
| **File** | `idle-warning-dialog.component.spec.ts` |
| **State** | 🔴 RED — module-resolution until Dev creates `IdleWarningDialogComponent` skeleton |

| | |

## Skipped (explicit)

| Topic | Reason |
|---|---|
| Multi-tab session sync | Implementation detail; cross-tab delivery is only meaningful in E2E (Playwright multi-context). `SessionSyncService` spec deleted. |
| BroadcastChannel fallback | Framework-level degradation, not a user-observable circuit. |
| Silent token refresh | Happens in background; user observes nothing. Already covered in existing `proactive token refresh timer` tests. |
| All individual permission combinations | Pattern verified once in existing `permissionGuard` tests; combinatorial coverage adds no new contracts. |
| Password reset variants | Out of scope per spec (link expiry is backend logic, not client circuit). |
| Network error / 5xx login messages | Nice-to-have; covered implicitly once HTTP 401 normalisation (Circuit 2) is implemented. |
| Expired token recovery | Already tested in existing `auth.service.spec.ts` (`handle401` + `checkSession` failure path). |
